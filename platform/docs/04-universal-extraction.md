# Build one ladder, not thirty-five adapters

Universality is achievable, but only at the discovery and transport layers — never at the semantic layer, and the reason is that **no standard, no vendor, and no page-type taxonomy anywhere in the 2026 web-extraction market models an auction bid**. schema.org has no `Auction` type and no `Bid` property; Diffbot classifies pages into five types and none is an auction; Zyte has ten and none is an auction; Oxylabs has no auction target at all. Every one of them collapses a lot page showing "Estimate $400–600 / Current bid $250 / Starting bid $100 / Buy It Now $750" into a single unlabelled `price`, which is not merely insufficient but a **silent-wrong-answer hazard strictly worse than a null**, because downstream a wrong pick is indistinguishable from a right one. The correct architecture is therefore not a universal extractor but a **universal fallback ladder** — sitemap and feed discovery, then a free JSON-LD/OpenGraph floor, then one-time headless network interception to find each site's own internal JSON API, then an LLM-generated deterministic extractor as the last rung — where each tier is one code path serving all sources and only a config row differs per site. The single most important cost fact is that **refresh, not first capture, is the entire budget**: capturing 50,000 lots once via a rented scraper costs $1,335–$7,500 a month, but re-polling those same live lots hourly through the same rented service runs to roughly **$54,000 a month at pay-as-you-go rates** ([Bright Data Web Scraper API pricing](https://brightdata.com/pricing/web-scraper)), whereas the adaptive closing-time ladder this project has already built and measured does the same job for bandwidth. That ladder — 25,000 requests/day for 5,220 tracked lots against 1,503,360 for uniform five-minute polling — is worth more than any vendor decision in this report, and the recommendation below is essentially "keep it, and feed it better sources."

## Refresh billing, not first capture, decides the architecture

Every price list in this market quotes a first-capture number and stays silent about the number that matters. Apify's auction actors publish per-result fees clustering at **$0.89–$5.00 per 1,000 lots** ([Apify solidcode/hibid-scraper](https://apify.com/solidcode/hibid-scraper/api), [scrapersdelight/govdeals-auction-scraper](https://apify.com/scrapersdelight/govdeals-auction-scraper/api), [delectable_incubator low-cost GovDeals](https://apify.com/delectable_incubator/govdeals-scraper-low-cost)); Bright Data's Web Scraper API quotes **$1.50 per 1,000 records** on pay-as-you-go, falling to roughly **$0.70 with commitment** ([Bright Data Pricing 2026 via Use Apify](https://use-apify.com/blog/bright-data-pricing-guide-2026)). Read as a first-capture cost these are trivially affordable. Read as a refresh cost they are ruinous, because auction data is only worth anything if current bid and time-remaining are fresh, and freshness means re-reading the same lot many times before it closes. Fifty thousand live lots re-polled hourly is 36 million records a month, which at pay-as-you-go lands near **$54,000/month and near $25,000/month even at committed rates**; the same arithmetic on Apify's $3/1,000 tier at twelve polls a day also reaches roughly **$54,000/month**. Per-record billing makes refresh a linear tax on exactly the behaviour that makes the data valuable.

This is where the work already done pays off, and it deserves to be stated as a measured result rather than a design intention. At 25,000 requests/day for 5,220 tracked lots, the adaptive ladder spends **4.8 fetches per lot per day**, against 288 for uniform five-minute polling — a **60× reduction**. Scaling that measured ratio linearly gives about 2.87 million refresh fetches/month at 20,000 tracked lots and 7.19 million at 50,000. Billed through a rented actor at even the cheapest observed $0.89/1,000, those refreshes cost roughly **$2,600 and $6,400 a month**; at $3/1,000 they cost **$8,600 and $21,600**. Run the same schedule uniformly at five minutes and the bill at $0.89/1,000 becomes roughly **$154,000 and $384,000 a month**. Self-fetched over pg_net against a discovered JSON endpoint, all of these numbers collapse to bandwidth and CPU inside infrastructure already paid for. The conclusion is blunt: the scheduler is the asset, per-record vendors are the liability, and any layer that bills per read must be confined to first capture and backfill.

The table below prices each candidate ingestion layer on the same basis. Assumptions are stated because they change the answer: a 30-day month, one billable result per lot per capture, 20,000 lots/day = 600,000/month and 50,000 lots/day = 1.5 million/month. Ranges reflect genuine unresolved conflicts between sources, flagged in the verification section.

|---|---|---|---|---|
| Own fetch + JSON-LD/OpenGraph floor | ~$0 marginal | bandwidth only | bandwidth only | Free; scales with the ladder |
| Own fetch + discovered internal JSON endpoint | ~$0 marginal after one browser pass | bandwidth only | bandwidth only | Free; cheapest refresh available |
| LLM generate-once deterministic extractor | $0.002–$0.092 **per site, one time** | ~$0 ongoing | ~$0 ongoing | Zero marginal LLM cost |
| Oxylabs (fetch only, your parser) | $0.95 plain / $1.25 JS-rendered / from $0.25 at volume | $150–$750 | $375–$1,875 | Linear per read |
| Bright Data Web Scraper API | $0.75–$1.50 (unresolved) | $450–$900 | $1,125–$2,250 | ~$54,000/mo hourly at PAYG |
| Rented Apify auction actors | $0.89–$5.00 | $534–$3,000 | $1,335–$7,500 | ~$54,000/mo at $3/1k, 12×/day |
| Diffbot Extract (+ third-party unblocker) | ~$0.90–$1.00 alone; ~$2.00–$2.50 with unblocker | $1,200–$1,500 | $3,000–$3,750 | Linear; $299/mo floor |
| Zyte fetch + `customAttributes` | ~$2–$4 (composed inference) | $1,200–$2,400 | $3,000–$6,000 | Linear; tier volatility risk |

| Browse AI robots | ~$69 per 1,000 runs | not viable | not viable | Credits deplete faster than expected |

Two rows deserve emphasis. **Firecrawl has no generate-once mode at all**, and its own documentation is explicit about why: `maxAge` caching delivers "500% faster response times," but "cached results still cost 1 credit per page, meaning caching improves speed and latency, not credit usage," while JSON mode costs **5 credits per scrape (1 base + 4 for JSON mode)** on every page, forever ([Firecrawl fast-scraping docs](https://docs.firecrawl.dev/features/fast-scraping), [Firecrawl JSON mode docs](https://docs.firecrawl.dev/features/llm-extract)). And the LLM-per-page row spans a 45× range because **token payload dominates everything**: a product page after stripping navigation and scripts runs about 38,000–40,000 tokens, while full HTML averages closer to 570,000 ([Minexa on AI scraping costs at scale](https://www.minexa.ai/post/the-real-cost-of-ai-web-scraping-tools-at-scale-what-the-demos-don-t-show-you)). Boilerplate stripping is the single highest-leverage lever if you insist on per-page inference — which you should not, because the compile-once alternative is free.

The formal case for compiling once is stronger than any vendor's. The "Agentic Compilation" paper frames the problem as a **"Rerun Crisis"** and measures it: a 5-step workflow over 500 iterations costs a continuous LLM agent approximately **$150 in inference, or $15 even with 90% aggressive caching**, while a compile-and-execute architecture reduces per-workflow inference cost to **under $0.10**, with **per-compilation cost of $0.002–$0.092 across five frontier models** and **80–94% zero-shot compilation success** — a formal reduction from O(M×N) to amortised O(1) ([arXiv 2604.09718](https://arxiv.org/abs/2604.09718)). With per-compilation and per-page costs in the same $0.002–$0.09 band, **generate-once pays for itself after roughly one to two pages per site**. Note the honest caveat carried from the notes: that paper could not be read in full, so the model set, task corpus, and whether the extraction tasks were listing pages remain unverified, and "compilation success" may mean "produced a runnable blueprint" rather than "extracted all fields correctly."

## No universal extractor can tell a bid from an estimate

Diffbot is the purest universal-extraction play in the market and the clearest demonstration of the ceiling. Its Analyze API "visually analyzes a web page, identifies its 'page-type,' and determines which Diffbot extraction API (if any) is appropriate," routing to one of **articles, discussions, images, products or videos**, with everything else returning `"other"` ([Diffbot Analyze API docs](https://www.diffbot.com/docs/extract/analyze)). Diffbot separately claims 98% of the public web falls into roughly 20 standard page types "including article, product, discussion, image, video, event, job, lists" — but only those five have extractors behind them, and **auction is not among the twenty either**. Its Product ontology is unambiguously retail-shaped: `offerPrice`, `regularPrice`, `availability` as a Boolean, and `saveAmountDetails` decomposing a discount from list price ([Diffbot Product ontology](https://docs.diffbot.com/docs/ont-product)). An auction lot routed to that extractor produces one ambiguous `offerPrice` with no field telling you what it is. Pricing is genuinely cheap — **Startup $299/month, Plus $899/month, with overage at $0.001 and $0.0009 per credit** and one page extraction equal to one credit ([Diffbot credits docs](https://docs.diffbot.com/docs/how-credits-work)) — but Diffbot is also the weakest of the four at unblocking, and documents the workaround itself: when pages are blocked, "you can download the full HTML using a third-party proxy and then pipe that HTML to a POST request to Diffbot Extract" ([Diffbot proxies docs](https://docs.diffbot.com/reference/using-proxies)). On protected auction platforms you pay twice.

Zyte has folded its old AutoExtract product into Zyte API as ten ML-backed page types — **product, productList, productNavigation, article, articleList, articleNavigation, forumThread, jobPosting, jobPostingNavigation, pageContent** — and again none is an auction ([Zyte automatic extraction docs](https://docs.zyte.com/zyte-api/usage/extract/index.html)). Its `price` is explicitly "the price at which the product is being offered at the moment" and `regularPrice` "the price before any discount," a markdown model rather than a bid model ([Zyte Product Extraction docs](https://docs.zyte.com/automatic-extraction/product.html)). But Zyte alone ships a real escape hatch, and it is the most plausible off-the-shelf route to auction semantics found anywhere in this research: **`customAttributes` with the `"extract"` method locates user-defined string, integer and number fields on any page for a flat $0.001 per request**, with a generative `"generate"` method available at $0.002/1k input and $0.01/1k output tokens for anything needing transformation ([Zyte custom attributes docs](https://docs.zyte.com/zyte-api/usage/extract/custom-attributes.html)). You supply the schema — `currentBid`, `startingBid`, `bidCount`, `lotNumber`, `closesAt`, `buyersPremiumPct` — and an LLM fills it. Zyte also has the best independently measured fetch success rate of the four, "consistently exceeding 90% on protected targets" in Proxyway's fifteen-site benchmark against Oxylabs' 85.82% ([Proxyway API comparison](https://proxyway.com/research/comparing-popular-web-scraping-proxy-apis)), and is the only vendor whose own docs concede that automatic extraction "is not magic — it should be tested on edge cases, localized pages, and long-tail targets before relying on it" and that new model versions "may become less accurate for specific fields of specific websites."

Bright Data inverts the premise entirely. It is not a universal extractor but roughly **600 to 800 per-site pre-built scrapers** — the count is quoted inconsistently across Bright Data's own properties, which is itself a signal — and it is the only vendor of the four with **named, pre-built auction scrapers**: HiBid, BidSpotter, Proxibid, Invaluable, AuctionZip, K-BID, Public Surplus and Cars & Bids, whose advertised HiBid output includes "lot title, auction house, **lot number**, **estimate range**, **current bid**, auction date, category, condition, location, images, and more" ([Bright Data HiBid Scraper](https://brightdata.com/products/web-scraper/hibid)). That proves auction semantics can be bought — but only site by site, which is per-platform configuration under a different name. Its Scraper Studio, which generates scraper code from a plain-English prompt and lets you "update it with a plain-language prompt instead of rewriting selectors" ([Bright Data Scraper Studio docs](https://docs.brightdata.com/products/scraper-studio/overview)), is best read as **build faster, not no build**. Oxylabs, finally, is a fetch-and-unblock layer with free parser tooling: a free Custom Parser driven by your own XPath/CSS ([Oxylabs Custom Parser docs](https://developers.oxylabs.io/scraping-solutions/web-scraper-api/features/custom-parser)), a free LLM-based OxyCopilot that "generate[s] scraping codes and parsing templates using simple prompts" ([Oxylabs AI Web Scraper](https://oxylabs.io/products/scraper-api/ai-web-scraper-copilot)), and dedicated targets covering Amazon, Walmart, eBay, Etsy and a dozen more marketplaces but **no auction site except eBay** ([Oxylabs API targets](https://developers.oxylabs.io/api-targets)).

Two structural facts finish the argument against all four as a primary layer. First, **auction data is not a superset of product data — the temporal semantics differ**. `currentBid` and `bidCount` are monotonically changing series against a hard deadline; `price` is a slowly varying scalar. Nothing in any of these retail schemas carries a per-lot close time, which means **this project's adaptive scheduler would have no input field to key off** regardless of extraction accuracy. That is disqualifying on its own. Second, broad schemas are precisely where LLM extraction breaks: ExtractBench finds "schema breadth and output volume — not document length or nesting depth — are the dominant predictors of extraction failure," with frontier models producing **0% valid output on a 369-field schema** ([arXiv 2602.12247](https://arxiv.org/abs/2602.12247)) — directional only, since ExtractBench measures PDF documents rather than web pages. The practical consequence aligns neatly with Zyte's cheap method: keep any LLM auction schema **narrow and flat, six to eight scalar fields**, and never ask one call for a 40-field lot record. And hold the extractor to the null discipline third-party auction scrapers already observe — "if a page shows no reserve, the reserve field is left null" rather than invented ([Apify MaxSold Scraper](https://apify.com/scrapersdelight/maxsold-scraper)).

## Renting works for first capture and bankrupts you on refresh

The rentable supply is deeper than expected. The Apify Store in September 2026 carries roughly **ten distinct publishers with HiBid actors, twelve with GovDeals actors and six with PublicSurplus actors**, plus dedicated actors for GSA Auctions, Municibid, Bid4Assets, AuctionZip, Proxibid, MaxSold, K-BID, Equip-Bid, StorageTreasures, Copart, Bring a Trailer and NetBid — and a **multi-site aggregator that searches eight auction sites in one run at $4 per 1,000 lots** ([Apify multi-auction-search](https://apify.com/scrapersdelight/multi-auction-search/api/mcp)). Field coverage is genuinely deep and genuinely auction-shaped, which no universal extractor achieves: the GovDeals actor returns "title, seller agency, category, current bid, bid count, bid increment, buyer's premium, buy-now price, closing time, quantity, condition, VIN, meter, city/state and photos" ([Apify scrapersdelight/govdeals](https://apify.com/scrapersdelight/govdeals-auction-scraper/api)); PublicSurplus adds "pick-up address, photos, attached documents … and an optional NHTSA VIN decode" ([Apify scrapersdelight/publicsurplus](https://apify.com/scrapersdelight/publicsurplus-scraper/api)); Municibid returns **realized sold prices on ended lots** ([Apify scrapersdelight/municibid](https://apify.com/scrapersdelight/municibid-scraper)). Notably, `primeselectai/us-federal-surplus-industrial-auctions` "monitors normalized U.S. federal surplus … from the documented GSA Auctions API" ([Apify primeselectai](https://apify.com/primeselectai/us-federal-surplus-industrial-auctions)) — which is to say, someone is charging $2.50 per 1,000 records to wrap the official API this project already has an adapter for. Where an official API exists, renting is the wrong shape of dependency.

The maintenance contract is the problem. Apify runs automated daily tests and will flag an actor "under maintenance" after three consecutive failures and deprecate it after another 28 days — but that test only checks "if an Actor can successfully run with its default input within 5 minutes," verifying nothing about whether fields are populated ([Apify Actor testing docs](https://docs.apify.com/actors/publishing/test)). Community publishers are "**solely responsible** for their Community Actors and **have no obligation to maintain, update, or provide support**" ([Apify help on community Actors](https://help.apify.com/en/articles/6999799-what-are-apify-maintained-and-community-maintained-actors)), with a **14-day window** to respond to a reported issue ([Apify Store Publishing Terms](https://docs.apify.com/legal/store-publishing-terms-and-conditions)). The failure mode to design for is therefore not an error but **fewer rows, or rows with null closing_time** — and it is already happening in this niche, with a HiBid publisher warning that HiBid "may have changed its GraphQL schema, which can cause **fields to stop filling**" and asking users to email a run ID ([Apify getascraper issues](https://apify.com/getascraper/hibid-scraper/issues)). The canonical precedent for class-wide breakage is the 2026 Reddit-scraper collapse, when Reddit deprecated its public JSON endpoints and every dependent actor broke at once ([ScrapeBadger on Reddit scrapers](https://scrapebadger.com/blog/why-every-reddit-scraper-broke-and-how-scrapebadger-fixed-it)). Two further points close the rent case. The **rental pricing model is fully retired on 1 October 2026**, with non-migrated actors auto-moved to pay-per-usage at zero revenue for the developer ([Apify migration blog](https://blog.apify.com/migrating-to-pay-per-event-pricing/)) — a strong incentive for marginal publishers to abandon rather than migrate, making Q4 2026 an unusually bad moment to take a new rental dependency. And renting makes the legal position **worse, not better**: Apify's General Terms state that if you extract data "from unauthorized sources, you shall be responsible for compensating any damages," require you to indemnify Apify, and cap Apify's own liability at the fees you paid in the preceding twelve months ([Apify General Terms](https://docs.apify.com/legal/general-terms-and-conditions)). You add a second contract on top of the same target-site exposure you had anyway.

The most under-priced finding in the research is that **the aggregation has already been built twice and is licensable**. BidProwl publishes "a REST API and MCP server over every listing and sold-price stat" with a **free tier of 1,000 calls a month**, covering "46,000+ government surplus auctions from 27 sites … across all 50 states" plus "sold prices from 230,000+ closed auctions … from 26 official sources," with per-family feeds refreshed every 30 minutes but capped at 50 newest items ([BidProwl research](https://bidprowl.com/research)); its homepage separately advertises 75,000+ listings, so treat coverage as 46k–75k. Its terms forbid scraping it, so the API is the only sanctioned path ([BidProwl ToS](https://bidprowl.com/terms)). GovAuctions.app sells "a paid Data API for developers and AI agents, as well as bulk data licensing … as scheduled exports," with free API keys available and a hosted MCP server ([GovAuctions.app about](https://govauctions.app/about)). Neither publishes a price, so both are procurement conversations. But GovAuctions.app also publishes something you can use this week for nothing: **a free, copyright-clean CC-BY 4.0 dataset of every completed federal GSA surplus auction lot with prices, bids, conditions and locations, in CSV and JSON, refreshed monthly** ([GovAuctions.app open dataset](https://govauctions.app/research/open-dataset)), mirrored as **`govauctions/us-gsa-surplus-auctions`, 11.7k rows** ([Hugging Face](https://huggingface.co/datasets/govauctions/us-gsa-surplus-auctions)). That is 11,700 rows of known-good closed lots — the ready-made ground-truth corpus for validating every extractor you build or rent, and the cheapest thing of real value in this entire report. Copart likewise publishes its own **CSV sales data** directly ([Copart](https://www.copart.com/content/us/en/buyer/sales/download-sales-data)), which makes both the Apify Copart actor and the paid Copart datasets hard to justify.

## The standardised layer is free, generic, and silent about bids

### schema.org has no Auction type, and Google has no auction rich result

There is no `Auction`, `Bid`, `AuctionListing`, `currentBid`, `bidCount`, `reservePrice` or `minimumBid` anywhere in the schema.org core vocabulary. `Offer` is defined around retail and rental examples — "an offer to sell tickets to an event, to rent the DVD of a movie … to repair a motorcycle" — with auctions absent from the enumerated list ([schema.org/Offer](https://schema.org/Offer)). The nearest thing to an auction class is a third-party DBpedia-derived term, `productontology.org/doc/Auction`, meant to be attached via `additionalType` ([Product Types Ontology](http://www.productontology.org/doc/Auction)); the nearest in-vocabulary event type, `SaleEvent`, describes a sale event rather than a lot or a bid ([schema.org/SaleEvent](https://schema.org/SaleEvent)). Open proposals in the pricing area concern retail semantics only — a `priceCategory` property and a `PriceTypeEnumeration` with values like "Installment" and "Subscription" ([schemaorg#2712](https://github.com/schemaorg/schemaorg/issues/2712), [schemaorg#2689](https://github.com/schemaorg/schemaorg/issues/2689)) — and no auction proposal surfaced in the issue tracker. The maximum a site can express in standard vocabulary is `Product` → `Offer` with `price` holding the current high bid, `priceCurrency`, `availability`, and a close time in one of `availabilityEnds`, `validThrough` or `priceValidUntil`. A generic crawler should read all three and treat the earliest plausible future timestamp as the close.

Google's position hardens this into a disincentive. Google has no auction structured-data type, no auction rich result and no auction guidance; Merchant Center automatic item updates require `price`, `priceCurrency`, `availability` and `condition` ([Merchant Center structured data](https://support.google.com/merchants/answer/7331077?hl=en)), and merchant-listing guidance requires that the marked-up price be what a user "would actually pay at that time" ([Google merchant listing docs](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing)). For a live auction, the honest price changes constantly and will routinely disagree with whatever Google last cached. And in the one adjacent vertical where Google says anything at all, it says no: "**Vehicle auctions and auction pricing are not supported**" ([Google Vehicle listings policy](https://developers.google.com/vehicle-listings/reference/policy)). That is the clearest available evidence that Google's listing programs are architecturally built around static prices, and the most likely reason auction platforms under-mark up relative to fixed-price retail.

Prevalence nonetheless makes a generic pass worth building, as a floor rather than a source. In the October 2024 Common Crawl extraction, **51.25% of 2.4 billion crawled pages and 44.12% of 37.4 million pay-level domains carried some embedded markup**, totalling 74 billion quads ([WDC extraction report](https://webdatacommons.org/structureddata/2024-12/stats/stats.html)); the HTTP Archive put **JSON-LD on 41% of pages in 2024, up from 34% in 2022, with OpenGraph on 64% and Twitter meta tags on 45%** ([Web Almanac 2024](https://almanac.httparchive.org/en/2024/structured-data)). Page-level adoption grew from 5.7% in 2010 to 46.9% in 2022, with JSON-LD passing 60% of annotating sites while hCard microformats fell from 66% to 27% ([Brinkmann et al., WWW 2023](https://www.uni-mannheim.de/media/Einrichtungen/dws/Files_Research/Web-based_Systems/pub/Brinkmann-etal-TheWDCSchemaorgDataSetSeries-WWW2023.pdf)). But `Product`-class markup is a much thinner slice — roughly **600 million products from over 2 million domains**, growing from 594K to 2.6M domains over five years ([WDC subsets](https://www.webdatacommons.org/structureddata/2024-12/stats/schema_org_subsets.html)) — and it is concentrated in Shopify/WooCommerce/Magento storefronts that emit it by default. Auction platforms are bespoke applications, so that default-on effect does not reach them. The practical ranking for a fallback ladder, ordered by expected yield, therefore puts **OpenGraph much higher than its reputation suggests**: JSON-LD `Product`/`Offer` first, then microdata, then OpenGraph `og:title`/`og:image`/`og:url` plus `product:price:amount`, then embedded application state, then microformats last.

Discovery, by contrast, is genuinely solved. The Sitemaps protocol is frozen, unversioned and near-universally implemented, with hard limits of **50,000 URLs and 50MB uncompressed per file** and index files to compose them ([sitemaps.org protocol](https://www.sitemaps.org/protocol.html)). `lastmod` in W3C Datetime is the only freshness hint search engines still read, and the protocol explicitly endorses the cheapest possible change-detection loop: "list the URLs that change frequently in a small number of Sitemaps and then use the `lastmod` tag in your Sitemap index file … Search engines can then incrementally crawl only the changed Sitemaps." **`changefreq` and `priority` are dead** — Google ignores both, a position restated by John Mueller and by Gary Illyes calling them "a bag of noise" ([SEO Component](https://www.seocomponent.com/blog/ignore-priority-changefreq-fields-sitemap/)) — so the crawler should not read them. Framework ubiquity is why coverage is high: sitemap generation is first-class in Django and in Yoast for WordPress ([Django sitemaps](https://docs.djangoproject.com/en/6.0/ref/contrib/sitemaps/)). There is a structural mismatch to respect, though: lots live days to weeks, and a sitemap is a static snapshot, so `lastmod` is a hint to re-fetch and never a substitute for polling a lot with a known close time. RSS is thinner but not worthless. No native feed was confirmed on any major auction platform, but GSA does publish a real feed for federal vehicle auctions ([GSA Fleet Auto Auctions RSS](https://fleetautoauctions.gsa.gov/html/static/rss.htm)), AuctionZip ships a WordPress "Feeds Plugin" that displays "auction listings and photo galleries … as soon as they are posted" ([AuctionZip](https://www.auctionzip.com/cgi-bin/feedlink.cgi)) — implying a per-seller feed endpoint worth probing — and TopAuctions24-7 offers free XML feeds of recent and same-day auctions ([TopAuctions24-7](https://www.topauctions24-7.com/page.php?page=rss)). Probing `/feed`, `/rss.xml`, `/atom.xml` and `<link rel="alternate">` costs one request and occasionally pays off on the small WordPress-based auctioneer sites that make up the Wisconsin long tail. `llms.txt` is not worth the request: **8.7% of the top 1,000 sites publish one, and 97% of roughly 38,000 valid files received zero requests in May 2026** ([ppc.land](https://ppc.land/llms-txt-adoption-rises-8-8x-but-97-of-files-get-zero-ai-requests/), [Rankability](https://www.rankability.com/data/llms-txt-adoption/)).

### There is no auction RESO, and the incentives guarantee there won't be

This should be stated without hedging: **there is no auction-industry equivalent of RETS/RESO.** No standards organisation, no published schema, no certification program, no compliance mandate, no shared transport. Searches for an auction data standard or an "AuctionML" return only other industries' formats — ACES/PIES for the automotive aftermarket, cXML for Ariba procurement, UNIDOC for EDI — plus academic auction reference models and the XMark synthetic benchmark, none of which is an interchange standard ([Springer auction reference model](https://link.springer.com/chapter/10.1007/3-7908-1624-8_16)).

The reason is structural, not accidental, and it is worth understanding because it tells you not to wait. Real estate standardised because it had a cooperative-compulsion substrate: brokers must share inventory to transact with each other, MLSs are member-owned cooperatives, and NAR could **mandate** compliance by policy through Handbook Policy Statement 7.90 ([NAR Handbook §12](https://www.nar.realtor/handbook-on-multiple-listing-policy/operational-issues-section-12-real-estate-transaction-standards-rets-policy-statement-790)), which is how RETS became "the standard for listings syndication" and how RESO later deprecated it in favour of the RESO Web API ([Realtyna RETS 101](https://realtyna.com/blog/what-is-rets/)). Auctions have none of that. Auctioneers do not need each other's inventory, the marketplaces are for-profit competitors whose catalogues *are* the moat, and the trade association has gone affirmatively the other way: in July 2021 the NAA Board issued a position statement recommending "**exclusive data ownership by auction entrepreneurs** in order to promote their own brand, drive traffic to their own websites and create their own online marketplaces," backed by survey data showing **70.4% of members use a third-party vendor to manage bidder, sales or seller information while only 55.4% understand how that vendor handles it** ([NAA Data Resources](https://www.auctioneers.org/data%20resources)). A trade body telling members to enclose their data will not sponsor a shared schema. This is an **equilibrium, not a gap about to close**.

The corollary is that write APIs exist and read APIs do not — a deliberate asymmetry, since marketplaces want supply and want to keep demand-side data. Exactly one ingest API has a public landing page: **Invaluable's Catalog Upload API**, which lets houses "add, edit, or delete lots in Timed and Live sales on Invaluable, AuctionZip and Private Label sites directly from their auction management software," and is "provided to auction management software companies" only ([Invaluable API Information](https://www.invaluable.com/inv/apiinfo/)). Proxibid's ingest is a CSV "Bulk Loader" with **interactive column mapping** — meaning it accepts arbitrary headers and asks the user to map them, which is the opposite of a standard but does make the field vocabulary discoverable ([Wavebid: Link and Export to Proxibid](https://wavebid3.zendesk.com/hc/en-us/articles/115004794806-Link-and-Export-to-Proxibid)). HiBid ingests through a private "Integrated Web Service" from Auction Flex plus an in-product CSV template ([Auction Flex IWS walkthrough](https://w.auctionflex.com/IWS_Walk_Through.htm)). The single genuinely public, documented API in the landscape is **RainWorx AuctionWorx** — ASP.NET Web API 2, REST-like, Create/Update/Get/Delete Listings ([AuctionWorx for Developers](https://www.rainworx.com/AuctionWorx/Developers)) — and it exists because RainWorx sells software rather than audience, which means it is a long tail of thousands of per-licensee endpoints rather than one tap. Two details are decisive. Cataloguing vendors advertise "exports to N platforms" as a feature: Gavelist maintains "**12+ export formats** including HiBid CSV, AuctionFlex 360, LiveAuctioneers, Proxibid, AuctionZip, BidWrangler, and Wavebid" plus a fallback generic CSV ([Gavelist Integrations](https://gavelist.com/integrations)), and AuctionWriter targets about ten ([AuctionWriter](https://auctionwriter.com/)). A vendor maintaining twelve dialects is telling you there is no thirteenth shared one. And Wavebid — an ATG product — documents that to list one auction on both Proxibid and BidSpotter, both also ATG brands, you must "use the .CSV file that was generated from Wavebid to upload the catalog directly into the BidSpotter/GAP Toolbox system … **this step will need to be repeated every time**" ([Wavebid dual listing](https://support.wavebid.com/hc/en-gb/articles/360016617298-Dual-Listing-Live-Auctions-on-Proxibid-and-Bidspotter)). If one corporate family cannot share a catalogue format internally, no industry standard is imminent.

One asset falls out of this section and is directly useful for Wisconsin-first expansion: the NAA's public "Find an Auctioneer" directory is searchable by name, company, city, state, ZIP, specialty and designation, with individually addressable profiles at the stable pattern `faa.auctioneers.org/profile.php?auctioneer={id}` ([NAA member directory](https://www.auctioneers.org/AF_MemberDirectory.asp), [example profile](https://faa.auctioneers.org/profile.php?auctioneer=45338)). That is a **sequentially enumerable ID space** and the best source-discovery surface found anywhere in this research — a seed list of US auction houses and their own websites, which is where the canonical catalogue actually lands. Membership is a subset rather than a census, so treat it as a seed, not the universe.

## Intercepting the network once turns thirty-five adapters into one harness

The layer that actually delivers universality is the one nobody sells. Modern listing sites are "shells that load a blank page and then make a second request to an internal API to get the data as JSON, and if you can find that API, you get perfectly structured data at 100x the speed" ([DEV: finding hidden APIs](https://dev.to/zilton7/the-faster-way-to-scrape-finding-hidden-apis-in-modern-websites-4n58)). The generic pipeline is to drive a real Chromium over CDP and read the JSON the site's own frontend fetches — "connecting a real browser over the Chrome DevTools Protocol, listening to the traffic it makes, and reading the JSON the site already produces for itself" ([Scrapeless](https://www.scrapeless.com/en/blog/network-request-interception-scraping-browser)). Playwright exposes this at four levels: passive `page.on('response')`, active `page.route()`, targeted `page.expect_response("**/api/...")`, and whole-context HAR recording via `record_har_path`, which "allows you to capture all network traffic for the entire context until the context is closed" ([Playwright Mock APIs docs](https://playwright.dev/docs/mock)). **HAR recording is the right default for a discovery pass** — one option, zero per-site code, offline analysis, and it sidesteps the "body already consumed" class of error that plagues live interception. Active interception introduces a real hazard: in Puppeteer every path in the handler must end in exactly one of `request.continue()`, `request.abort()` or `request.respond()`, "or the unanswered request will hang until it times out" ([DEV: mastering request interceptions](https://dev.to/saairaam/mastering-request-interceptions-in-puppeteer-e75)).

The documented limits bound what is discoverable. `Fetch.getResponseBody` "may only be issued for a request that is paused in the Response stage"; "the response body is not available for redirects"; and "**WebSocket, Server-Sent Events, and Stream responses are not interceptable using CDP**" ([CDP Fetch domain](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/)). Traffic from iframes, nested iframes and service workers is reported as not intercepted ([playwright#21816](https://github.com/microsoft/playwright/issues/21816)). Live-bid platforms that push updates over WebSocket therefore need `Network.webSocketFrameReceived`-style handling rather than Fetch-domain body capture — a real constraint to plan for, not an edge case, on any platform with a live outcry mode. The spec-generation half of the pipeline is mature OSS: `mitmproxy2swagger` turns mitmproxy captures **or browser HAR exports** into OpenAPI 3.0, "allowing you to automatically reverse-engineer REST APIs by just running the apps and capturing the traffic" ([alufers/mitmproxy2swagger](https://github.com/alufers/mitmproxy2swagger)), with a faster Rust rewrite in `mitm2openapi` ([Arkptz/mitm2openapi](https://github.com/Arkptz/mitm2openapi)).

The selection half — deciding which captured response holds the listing data — is **a genuine literature gap**, and the report should say so plainly: no peer-reviewed or formally published work on scoring network responses to find the data endpoint surfaced at all, and the academic web-extraction corpus is overwhelmingly DOM-based wrapper induction. The complete algorithm nonetheless exists as practitioner recipe: filter to XHR/fetch responses with a JSON content type, "log the URLs of JSON responses **containing a target string**, locate the precise value inside that JSON, then **traverse all sibling objects and extract the full array**" ([Browserless](https://www.browserless.io/blog/json-responses-with-puppeteer-and-playwright)). Turning that into a scorer means combining token-overlap recall — the fraction of distinct visible strings scraped from the rendered DOM (titles, prices, lot numbers, dates) that appear as values in the JSON — with a repeated-shape score over key-set Jaccard similarity, and a **cardinality match between array length and the number of rendered result cards**, which is the strongest disambiguator because it separates the true listing endpoint from config, telemetry and i18n bundles that also echo page strings. No source states or evaluates this, so it must be measured in-house; there is no external number to quote.

Replaying the discovered endpoint, not finding it, is the hard part in 2026. Cloudflare, DataDome, Akamai and PerimeterX "read the TLS fingerprint before a single byte of HTML is sent," so a naive `requests` call to a discovered endpoint is flagged before any header is examined ([apiserpent](https://apiserpent.com/blog/bypass-cloudflare-datadome-scraping)). The industry answer is a hybrid: `curl_cffi` "can impersonate browsers' TLS/JA3 and HTTP/2 fingerprints" ([curl_cffi FAQ](https://curl-cffi.readthedocs.io/en/v0.7.1/faq.html)) but runs no JavaScript, so "let a real browser solve the challenge once, grab the `cf_clearance` cookie, then hand it to curl_cffi for all the fast follow-up requests. **You pay the browser tax once instead of on every call**" ([Datahut](https://www.blog.datahut.co/post/web-scraping-without-getting-blocked-curl-cffi/)). That generalises into a clean component boundary: one long-lived headless session per site acting as a **token broker**, re-minting short-lived tokens on 401/403, while N cheap HTTP workers do the paginated fetching. The economics justify it decisively — **€0.10 per 1,000 direct HTTP requests versus €1.00 per 1,000 full-browser requests, a 10× gap** ([Scrappey](https://scrappey.com/features/headless-browser)) — and headless runs "roughly an order of magnitude slower per page than a plain HTTP request" ([Crawlex](https://blog.crawlex.net/blog/headless-browser-tax/)). A one-time discovery pass is a handful of browser page loads plus one bounded LLM call, which puts it **well under a cent to a few cents per site**; against even one month of collection that is noise, so re-discovery can fire weekly and the JSON route still wins by roughly 10×. Two cases defeat the hybrid and should be budgeted as browser-cost sites: **request signing**, where an HMAC over path, body and timestamp is computed inside the site's JS bundle and cannot be replayed from an HTTP client, and GraphQL **persisted queries**, where the client sends only a hash the server must recognise — for which the correct discipline is to capture and replay the exact operation document or hash verbatim and vary only `variables`.

Now the asymmetry that should drive the monitoring design, because it is the strongest single argument for endpoints over selectors. Practitioner consensus is that internal endpoints outlast CSS selectors — "frontend developers change HTML structure and CSS classes all the time … but they rarely change the internal API structure" ([DEV](https://dev.to/zilton7/the-secret-to-fast-web-scraping-finding-internal-json-apis-11h5)) — with Scrapfly listing stability as an explicit benefit while conceding that "hidden APIs are not documented and can change at any time" ([Scrapfly: how to scrape hidden APIs](https://scrapfly.io/blog/posts/how-to-scrape-hidden-apis)). The mechanism is plausible even absent measurement: an internal API is a contract between deployed clients and a server, and old app versions keep consuming it, whereas Tailwind or CSS-modules class names are **generated build artifacts that change on every rebuild**. But the durability claim is practitioner consensus, not measured fact, and every source making it sells tooling. **The failure mode difference is the real advantage.** Endpoint breakage fails loudly — non-200 status, content-type no longer JSON, JSONPath miss, zero-length array, cardinality collapse — while selector breakage degrades silently, returning structurally valid records with empty or wrong fields. "Silent failure is worse than a crash" is the practitioner framing ([Ficstar](https://ficstar.medium.com/why-web-scraping-fails-silently-and-why-thats-worse-than-a-crash-2b4a8f615ccf)), and the operational consequence is that **loud failures are cheap, crisp triggers for automated re-discovery** in a way that silent ones never are. Those triggers map one-to-one onto the `source_health` columns this project already has: a drift_ratio spike or a per-field null-rate jump on `current_bid` or `closes_at` is exactly the signal to re-run a discovery pass.

Where the endpoint route fails, the generate-once selector route is the fallback, and one tool implements the whole loop as first-party API surface. Crawl4AI's docs state the economics outright: "**One-Time Cost**: While schema generation uses LLM, it's a one-time cost. **The generated schema can be reused for unlimited extractions without further LLM calls**" ([Crawl4AI no-LLM strategies](https://raw.githubusercontent.com/unclecode/crawl4ai/main/docs/md_v2/extraction/no-llm-strategies.md)). `generate_schema` is a static method on `JsonCssExtractionStrategy` and `JsonXPathExtractionStrategy`, it **validates the generated schema against the HTML and "automatically refines the selectors before returning"** if it produces no results, it supports a `TokenUsage` accumulator for tracking the one-time cost, and it runs against OpenAI or against **Ollama with no API token**. Its multi-sample guidance is the part that matters most for auction sites, whose lot templates vary: generating from one page yields `tr:nth-child(6) td a`, which fails on the next page where the field sits in row 5, while generating from several samples with an explicit instruction to prefer href patterns, data attributes and class names yields `a[href*="/m/"]` — letting you "generate schemas once that work reliably across hundreds of similar pages with varying structures." The same pattern exists for regex via `generate_pattern` with an on-disk `pattern_cache/`, and Crawl4AI actively steers users away from per-page inference: "LLM-based extraction can be slower and costlier … consider using `JsonCssExtractionStrategy` … first." LLM Scraper offers the TypeScript equivalent, where `scraper.generate()` produces "re-usable playwright script" ([llm-scraper](https://raw.githubusercontent.com/mishushakov/llm-scraper/main/README.md)) — more expressive than a declarative selector set, but arbitrary JavaScript is harder to diff and review across dozens of auto-regenerated extractors. For cosmetic churn there is a free, LLM-free healing layer beneath both: Scrapling records "a structural profile of the matched element" with `auto_save=True` and relocates it by similarity scoring with `adaptive=True` after a redesign ([ScrapingBee on Scrapling](https://www.scrapingbee.com/blog/scrapling-adaptive-python-web-scraping/)), which composes into the cascading fallback chain a job-scraper project already ships as **CSS → JSON-LD → regex → Scrapling, with a 0-result canary** ([peviitor-scraper-py](https://github.com/TheTatu13/peviitor-scraper-py)).

Every credible design in this space converges on one rule, and it should be written into the promotion logic: **the LLM proposes, a deterministic validator disposes.** webmedic's "deployment decisions are always controlled by deterministic validation" ([webmedic-scrapeverse](https://github.com/gundujeevesh123/webmedic-scrapeverse)), the self-healing recipe's "only verified selectors are written to the selector configuration" ([DEV: building a self-healing scraper](https://dev.to/ahmed_shamandy_17cae30af0/building-a-self-healing-scraper-let-ai-fix-your-selectors-when-sites-change-2maj)), and Crawl4AI's generation-time validation all say the same thing. In hybrid pipelines the discipline extends to values: "**deterministic values always override LLM outputs for comparison-critical fields**," and without that merge rule "LLM extraction introduced noise into fields where deterministic parsing was already accurate" ([GroupBWT](https://groupbwt.com/blog/llm-for-web-scraping/)). One class of failure escapes every automated check and explains why canaries are not optional: a schema that is **structurally valid but semantically wrong** — right types, wrong element matched after a redesign, picking up "Buy It Now" instead of current bid — passes Pydantic validation and every null-rate threshold. Only "a small set of pages whose correct values you already know … re-scrape[d] every run" catches it ([Context.dev](https://www.context.dev/blog/scraper-monitoring-in-production)). The GovAuctions CC-BY corpus is that canary set for federal lots, free and already normalised.

Finally, a calibration on accuracy that should temper any per-page-LLM ambition. Frontier models reach **F1 around 0.91** on e-commerce attribute extraction ([arXiv 2403.02130](https://arxiv.org/abs/2403.02130)), but **cost-efficient models collapse to F1 near 0.50 on MAVE**, and a 2026 paper's central finding is that **evaluation methodology dominates model choice** ([arXiv 2607.22949](https://arxiv.org/pdf/2607.22949)). That gap is the strongest argument *for* generate-once rather than against it: you can afford a frontier model for one-time synthesis per site, whereas per-page economics push you toward exactly the cheap models that score 0.50. It also means any published F1 is near-meaningless for auctions unless you define your own field-level matcher — price normalised to integer cents, dates to ISO-8601, location fuzzy-matched. **Build the evaluator before the extractor**; this project's money-as-cents and three-location schema decisions have already done half that work.

## What we could not verify, and the eight requests that settle it

This research was conducted with outbound fetching blocked for essentially every vendor and documentation domain, so almost everything above rests on search-result snippets rather than pages read in full. Two circulating accuracy figures are **excluded rather than reported**: a claimed "96.48% average accuracy for LLM-generated extraction functions," which appeared in an aggregated snippet attributed to an unnamed "2025 study" that could not be traced, and Kadoa's "98.4% accuracy even when page structures changed," which is vendor marketing with no methodology, corpus or baseline. Neither should enter a budget or a design document. A third figure — a frequently repeated claim that `schema.org/Product` has "an adoption rate of 1.50%" — has no traceable denominator or year and should not be used either.

The unresolved conflicts matter because they span the ranges that decide vendor selection, and they are cheap to close. Apify's Starter tier is quoted as both **$19 and $29** ([ScrapeGraphAI on Apify pricing](https://scrapegraphai.com/blog/apify-pricing), [use-apify](https://use-apify.com/docs/what-is-apify/apify-pricing)). Zyte's per-1,000 rates appear as "**starts at $0.06**" on its own page, as "**$0.13 for HTTP and $1.00 for browser-rendered**" in one summary, and as "**$0.06 to $16.08 across 5 tiers — a 268× spread**" in another, with the per-1,000 price of the `extract` capability itself never pinned down and with users reporting "**bills 40× higher than expected**" when retries, browser rendering and premium proxies cascade. Bright Data's per-record rate appears as **$0.75, $1.00 and $1.50**, unresolved. Firecrawl's own docs say JSON mode is 5 credits per page, while a competitor asserts `/extract` runs on a separate token subscription costing "$83–99/mo plus a ~$89/mo extraction add-on" — a direct contradiction. Whether Bright Data's HiBid and BidSpotter scrapers return **per-lot closing time (as distinct from auction date), bid count, or buyer's premium** is unconfirmed, since the field list was truncated at "and more" — and per-lot close time is the field this project's scheduler runs on. No per-actor success rate, last-modified date, user count or run count could be retrieved for any Apify auction actor, which is the single biggest gap in the rent option. Oxylabs' AI Studio pricing was not found at all. Neither BidProwl nor GovAuctions.app publishes a price, and for both the **redistribution right — whether a licence lets you re-expose the data in your own product — is unknown**, which is the decisive commercial term.

Beyond pricing, three evidence holes are structural rather than fixable by a fetch, and should be treated as permanent conditions of operating here. **No vendor publishes any auction-specific accuracy figure**; not one of the four makes a claim about bid-versus-estimate disambiguation. **No independent 2026 benchmark of extraction field accuracy exists for any of them** — the only reproducible extraction benchmark found is Zyte's own article-extraction dataset from 2019, on which Diffbot scored F1 0.951 ([article-extraction-benchmark](https://github.com/scrapinghub/article-extraction-benchmark)), which is competitor-run, seven years old, and measures article bodies. And **no measured breakage rate exists for anything**: not selector MTBF, not endpoint churn, not LLM regeneration success in production. Every durability claim in this report is mechanism plus practitioner consensus.

The good news is that the verification cost is close to zero, and it should be the first work item. Roughly **eight HTTP requests per platform collapses most of the unknowns**: one lot page grepped for `application/ld+json`, `itemscope`/`itemtype`, `og:` tags and `__NEXT_DATA__`/`__NUXT__`; `robots.txt` for the `Sitemap:` directive; `/sitemap.xml` and `/sitemap_index.xml` for lot-URL patterns and `lastmod` freshness; `/feed` and `/rss.xml` for a feed; and one search or list page recorded under Playwright HAR to see whether a listing JSON endpoint exists at all. For the eight major platforms that is 64 requests; across all 35 catalogued sources it is under 300, well inside an hour of wall time. Vendor claims are equally cheap to test, because every free tier is large enough for the only experiment that matters — running 200 to 500 real lot pages from the actual target platforms through each API and diffing returned fields against hand-labelled truth. Diffbot gives 10,000 credits at 5 calls/minute, Bright Data gives 5,000 records a month recurring, Zyte gives $5 of credit which covers thousands of `customAttributes` calls at $0.001 each, Oxylabs gives 2,000 results over 7 days, BidProwl gives 1,000 API calls a month, and GovAuctions.app gives a free key. Zyte and Bright Data bill only successful responses, so a blocked auction-site fetch costs nothing. **The entire buy-versus-build decision can be settled for $0 and a few days of labelling** — and it must be, because the public record contains no number that would settle it for you.

Item 4 is where the answer to the original question actually lives. The existing HiBid adapter is described as platform-shaped with runtime capability probing, and a third-party scraper vendor claims some solutions use "HiBid's own API … without requiring login credentials" — a low-confidence, vendor-grade claim that most plausibly means an undocumented internal JSON endpoint ([Apify lexis-solutions HiBid](https://apify.com/lexis-solutions/hibid-com-scraper/api)). If the HiBid adapter is already consuming an internal endpoint, then **the generic harness is a generalisation of code that already works**, not a new architecture, and item 4 should be scoped as refactoring the discovered-spec concept out of that adapter and into a table. The GSA adapter stays exactly as it is: an official API beats every tier in this report, and every hour spent on an official-API source is an hour not spent on the long tail.

Five things to stop or not start. **Do not buy Diffbot, Zyte or Oxylabs universal extraction as the bid source** — none models auction semantics, none carries a per-lot close time to drive the scheduler, and a single unlabelled `price` on a lot page is a silent wrong answer; Zyte's `customAttributes` at $0.001/request remains worth benchmarking as a *fallback for unreachable long-tail sites*, on a narrow six-to-eight-field flat schema, but only after the free probe shows where it would actually be needed. **Do not route refresh through any per-record vendor**: first capture at $1–3 per 1,000 is fine, hourly refresh at $54,000 a month is not, and the adaptive ladder already built is the reason you never have to. **Do not take a new Apify rental-model dependency in Q4 2026** — the rental model retires 1 October 2026 and marginal publishers have every incentive to abandon rather than migrate; if you rent at all, use pay-per-result actors and keep a second publisher's actor for the same site warm, which is cheap given ten HiBid and twelve GovDeals publishers. **Do not wait for a standard, a platform read API, or an NAA data committee** — none is coming, and the NAA's 2021 data-enclosure position statement is the reason. And **do not build ZIP-radius filtering, `llms.txt` ingestion, or PDF document AI into the crawler**: no rented actor exposes a radius primitive but GovDeals output carries lat/lng so radius belongs downstream in PostGIS; `llms.txt` reaches 8.7% of the top thousand sites with 97% of files receiving zero requests; and Extend.ai at **$50–$62.50 per 1,000 pages** is an order of magnitude above HTML extraction and only earns its price if you start ingesting PDF catalogues and condition reports.

## Conclusion

The framing that makes this tractable is that "universal" is three different problems wearing one word, and only two of them are solved. **Universal discovery** is genuinely free: sitemaps are a frozen, framework-generated, near-universal protocol whose index-level `lastmod` is the cheapest change-detection loop that exists, and it costs one code path. **Universal transport** is nearly free: one headless browser pass per site, amortised at a few cents, converts a bespoke frontend into a JSON endpoint that costs a tenth as much to read and fails loudly when it breaks. **Universal semantics does not exist and will not be built**, because the vocabulary has no bid field, the search engine that would incentivise one explicitly bans auction pricing in the only adjacent vertical where it has a policy, and the trade association has told its members to enclose their data rather than pool it. The mistake available here is to buy a product that promises the third thing and quietly delivers a retail `price` — which is worse than delivering nothing, because a null is visible in a null-rate report and a confidently mislabelled number is not.

What that implies for sequencing is slightly counterintuitive. The highest-value engineering is not extraction at all; it is the **evaluator and the loud-failure plumbing**. A field-level matcher graded against 11,700 free known-good federal lots, plus canary rows that catch the structurally-valid-but-semantically-wrong case that every automated check misses, is what makes every subsequent tier safe to automate — and it is what turns the existing `drift_ratio` and per-field null-rate columns from telemetry into a control loop that fires re-discovery. Build that first, and the ladder above can be added a rung at a time without ever again asking whether a source is trustworthy. Skip it, and the cheapest architecture in this report becomes the one that silently reports starting bids as current bids across thirty-five sources at once.
